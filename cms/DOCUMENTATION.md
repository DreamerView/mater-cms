### Мобильное боковое меню

На узких экранах drawer служит только для перехода между основными разделами: **Мой контент, Данные, Файлы, Формы, Настройки, О продукте, Корзина**. Дерево папок проекта и нижняя кнопка **«Новая папка»** в этом меню не показываются. Папки создаются и управляются внутри страницы **Мой контент**, поэтому навигация остаётся компактной и не дублирует файловую структуру.

## 1. Что такое MaterCMS

MaterCMS — лёгкая headless CMS для управления контентом сайта через простой интерфейс.

Вместо сложных понятий вроде «тип контента» и «коллекция» MaterCMS использует понятную модель:

```text
Проект
└── Папка
    └── Раздел
        └── Поля
```

Пример:

```text
Сайт компании
├── Главная
│   ├── Главный экран
│   └── SEO
├── О компании
└── Проекты
```

Сайт получает заполненные данные через API в формате JSON.

# 2. Установка

## 2.1 Требования

Для работы MaterCMS нужны:

- PHP 8.1 или новее;
- PDO;
- хотя бы один драйвер базы данных: `pdo_sqlite`, `pdo_mysql` или `pdo_pgsql`;
- расширение `fileinfo`;
- Apache/LiteSpeed, nginx, Caddy или другой web-сервер; clean URL через `.htaccess` доступны на Apache/LiteSpeed, а на остальных MaterCMS автоматически использует direct API route;
- права на запись для `cms/data/`;
- права на запись для `cms/uploads/`;
- доступ браузера к Vue 3 и Bootstrap Icons CDN.

Node.js, npm, Vite и сборка не нужны.

## 2.2 Куда загружать CMS

Рекомендуемая структура:

```text
public_html/
├── index.php
├── assets/
└── cms/
```

Основной сайт продолжает работать в корне домена, а MaterCMS находится отдельно.

```text
https://example.com/       — сайт
https://example.com/cms/   — MaterCMS
```

## 2.3 Первый запуск: выбор базы данных

При первом открытии `/cms/` MaterCMS показывает экран **«Где хранить данные?»** и сразу проверяет доступные PDO-драйверы PHP.

Первый шаг установки выполнен в том же минималистичном широкоформатном стиле, что и экран входа: слева краткое объяснение, справа — только выбор и настройка базы данных. На мобильном устройстве остаётся одна рабочая колонка.

Доступны:

- **SQLite** — локальный файл без отдельного сервера;
- **MySQL** — через `pdo_mysql`;
- **PostgreSQL** — через `pdo_pgsql`.

Если нужного расширения PHP нет, карточка СУБД будет недоступна. MaterCMS не позволяет продолжить установку с драйвером, которого нет на сервере.

### SQLite

SQLite остаётся самым простым вариантом: дополнительных полей нет. MaterCMS использует локальный файл в закрытом каталоге:

```text
cms/data/matercms.sqlite
```

### MySQL и PostgreSQL — сначала URL

Для MySQL и PostgreSQL MaterCMS **по умолчанию открывает режим URL**. Это удобно для облачных баз и хостингов, которые уже выдают готовую строку подключения.

MySQL:

```text
mysql://user:password@host:3306/database
```

PostgreSQL:

```text
postgresql://user:password@host:5432/database?sslmode=require
```

Пароль и другие части URL со специальными символами должны быть URL-кодированы.

### MySQL и PostgreSQL — режим «Поля»

Если URL неудобен, переключитесь на **Поля** и укажите:

- host;
- port;
- имя базы;
- пользователя;
- пароль;
- для PostgreSQL — `sslmode`.

MySQL/PostgreSQL database должна существовать заранее. MaterCMS создаёт внутри неё свои таблицы, но не создаёт саму database на сервере.

## 2.4 Проверка подключения

После нажатия **«Проверить и продолжить»** MaterCMS:

1. проверяет наличие выбранного PDO-драйвера;
2. разбирает параметры подключения;
3. действительно подключается к БД;
4. только после успешного соединения сохраняет конфигурацию.

Если соединение не удалось, конфигурация не активируется и MaterCMS показывает ошибку.

Конфигурация хранится в закрытом файле:

```text
cms/data/database.php
```

Пароль базы не передаётся в SPA и не возвращается через admin API.

## 2.5 Создание администратора

После успешного подключения базы MaterCMS переходит ко второму шагу:

1. укажите имя владельца;
2. укажите email;
3. задайте пароль минимум из 8 символов;
4. нажмите **«Установить MaterCMS»**.

MaterCMS создаст актуальную схему таблиц, владельца и первый проект.

## 2.6 Где посмотреть используемую СУБД

После установки откройте **Настройки → База данных**. Этот пункт открывает отдельную системную страницу.

MaterCMS показывает только безопасные сведения:

- SQLite / MySQL / PostgreSQL;
- состояние соединения;
- PDO-драйвер;
- имя базы;
- host/port для серверной СУБД;
- версию сервера.

Username, password и полный URL подключения в SPA не передаются.

## 2.7 Смена базы данных после установки

Владелец MaterCMS может открыть:

```text
Настройки → База данных → Сменить базу данных
```

Далее:

1. выберите SQLite, MySQL или PostgreSQL;
2. для MySQL/PostgreSQL по умолчанию открыт режим **URL**;
3. при необходимости переключитесь на **Поля**;
4. нажмите **«Проверить и перенести»**;
5. подтвердите перенос.

MaterCMS выполняет перенос в безопасной последовательности:

```text
проверка PDO-драйвера
        ↓
проверка соединения
        ↓
создание схемы MaterCMS в целевой БД
        ↓
копирование данных с сохранением ID
        ↓
проверка количества записей
        ↓
переключение cms/data/database.php
```

Если что-то не получилось, конфигурация текущей базы **не переключается**.

Целевая база не должна содержать другую заполненную установку MaterCMS. Исходная база после успешного переноса автоматически не удаляется — её можно сохранить как резервную копию.

> При переносе SQLite → MySQL/PostgreSQL или обратно убедитесь, что PHP-процесс не будет остановлен во время операции.

---

## 2.8 Вход в MaterCMS

После установки `/cms/` открывает экран авторизации MaterCMS. Введите email и пароль администратора или другого созданного пользователя.

Экран входа выполнен как широкоформатная поверхность без внешней карточки: на desktop интерфейс занимает весь viewport, а форма остаётся компактной и читаемой. На мобильном устройстве форма занимает экран без лишних декоративных панелей.

Если данные введены неверно, MaterCMS показывает ошибку внутри формы и не раскрывает техническую информацию об аккаунте.

# 3. Основной интерфейс

В MaterCMS есть пять основных рабочих зон:

- **Мой контент** — папки, разделы и значения полей;
- **Данные** — глобальные данные проекта;
- **Файлы** — изображения, видео, аудио и документы;
- **Формы** — формы сайта и входящие заявки;
- **Настройки** — проекты, пользователи, языки, API и системные параметры.

## 3.1 Универсальный поиск

В header MaterCMS находится **одна строка поиска для всей CMS**. Отдельные поиски для страницы файлов, форм или папки больше не нужны.

Отдельной глобальной кнопки **API** в header больше нет. Это освобождает верхнюю панель от контекстного действия: подключение API открывается непосредственно у нужной папки, раздела, набора **Данные** или формы, а настройки доступа проекта находятся в **Настройки → Доступ к API**.

Можно нажать на поиск или использовать:

```text
Ctrl + K
Cmd + K
```

Поиск текущего проекта умеет находить:

- папки;
- разделы;
- текст внутри разделов;
- наборы «Данные» и значения записей;
- формы;
- содержимое входящих заявок;
- файлы и места их использования.

Для владельца CMS поиск также находит проекты и пользователей.

Результаты сгруппированы по типу. Нажатие на результат сразу открывает соответствующий раздел MaterCMS. Панель поиска при переходе закрывается автоматически и не остаётся поверх нового экрана.

Поиск выполняется с небольшой задержкой после ввода, поэтому CMS не отправляет запрос на каждое нажатие клавиши.

## 3.2 Как устроена страница «Настройки»

Главная страница **Настройки** является центром переходов. На ней находятся пять навигационных карточек в четырёх группах настроек:

1. **Доступ к API** — отдельная страница Public / Private API текущего проекта;
2. **Языки проекта** — отдельная страница локализации;
3. **Проекты** — рабочие пространства, выбор проекта, участники, роли, точные права и системные действия;
4. **Команда** — учётные записи MaterCMS: создание, редактирование и удаление пользователей;
5. **База данных** — отдельная системная страница состояния СУБД и переноса между SQLite / MySQL / PostgreSQL.

То есть длинной страницы со всеми настройками подряд больше нет. Каждый раздел имеет собственный URL, хлебные крошки и кнопку возврата в настройки.

Интерфейс настроек использует единый визуальный язык: заметные белые/тёмные поверхности вместо бледных горизонтальных разделителей, одинаковые отступы и радиусы, читаемый размер подписей и отдельные адаптивные состояния. Страницы **Доступ к API, Языки проекта, Проекты, Команда и База данных** выглядят как части одной системы, а не как разные экраны.

На странице **База данных** состояние подключения оформлено как отдельная панель: сверху текущая СУБД и статус соединения, ниже — драйвер, имя базы, сервер и версия. Блоки безопасности, переноса и действие смены СУБД визуально отделены друг от друга. Это же оформление полностью поддерживает светлую, тёмную и системную тему.

Ниже блоков находится **Тема MaterCMS**:

- **Системная** — следует светлой/тёмной теме операционной системы;
- **Светлая**;
- **Тёмная**.

Выбор темы сохраняется локально в браузере и применяется ко всему интерфейсу MaterCMS. В системном режиме MaterCMS автоматически реагирует на изменение темы устройства.

Тёмная тема является полноценной цветовой схемой интерфейса: она применяется к header и глобальному поиску, карточкам и спискам, редакторам, формам, модальным окнам, offcanvas-панелям, dropdown и context menu, настройкам, проектам и пользователям, API-панелям, авторизации и мастеру установки. Отдельные состояния `hover / focus / disabled`, поля ввода, placeholder, предупреждения, ошибки и успешные статусы имеют собственные контрастные тёмные цвета. `theme-color` браузера также синхронизируется с фактически активной темой.

В заголовке настроек показывается текущий проект, чтобы было понятно, к какому рабочему пространству относятся API и языки. Пароли базы и полный URL подключения после сохранения не возвращаются во frontend.

## 3.3 Заголовки контента

На страницах папок MaterCMS не повторяет техническую подпись **«Контент»** над названием. Контекст уже виден в хлебных крошках `Мой контент → ...`, поэтому заголовок остаётся чище.

## 3.3 Плавные переходы между экранами

Внутренняя навигация MaterCMS работает без полной перезагрузки страницы, но при переходе теперь показывает короткую анимацию:

- текущий экран слегка приглушается;
- под header появляется тонкий индикатор перехода;
- новый экран мягко появляется после загрузки данных.

Это касается переходов в папки, разделы, данные, формы, файлы, проекты, пользователей и настройки. Если в операционной системе включено **Reduce Motion / Уменьшение движения**, MaterCMS отключает декоративную анимацию.

## 3.4 Умное контекстное меню

В MaterCMS можно нажать **правой кнопкой мыши** почти в любой рабочей области. Меню меняется в зависимости от того, на что вы нажали.

### Если нажать на объект

MaterCMS показывает действия именно для этого объекта. Например:

- папка — открыть, копировать, вставить внутрь, переименовать, удалить;
- раздел — открыть, открыть API, копировать, переименовать, удалить;
- запись `Multiple` — читаемый вид, редактирование, удаление;
- набор «Данные» — открыть или перейти к API;
- форма — открыть или посмотреть подключение/API;
- файл — предпросмотр, перейти к месту использования, скопировать ссылку, открыть оригинал;
- проект — открыть, а для текущего проекта также переименовать или удалить, если это разрешено;
- пользователь — редактировать или удалить;
- заявка формы — открыть или удалить;
- участник проекта — изменить права или убрать из проекта.

### Если нажать на пустое место

Меню относится ко всей текущей странице. Например:

- в «Мой контент» — создать папку/раздел, вставить объект из внутреннего буфера, сменить Grid/List, обновить;
- в «Файлах» — сменить Grid/List, обновить, очистить неиспользуемые файлы;
- в «Данных» — создать набор данных;
- внутри `Multiple` — создать запись, открыть поля/API и сменить Grid/List;
- в «Формах» — создать форму;
- в «Проектах» и «Пользователях» — создать новый объект или обновить список;
- в «Настройках» — быстро перейти к проектам, пользователям или базе данных.

Контекстное меню автоматически не выходит за края экрана, закрывается по `Esc`, по клику вне меню, при прокрутке или изменении размера окна.

MaterCMS **не подменяет системное контекстное меню** внутри полей ввода, textarea, ссылок, блоков кода и выделенного текста — там остаются привычные действия браузера «Копировать / Вставить / Открыть ссылку».

### Буфер обмена в «Мой контент»

На desktop MaterCMS ведёт себя как файловый менеджер:

- один клик по папке или разделу **выбирает** объект;
- двойной клик **открывает** его;
- `Ctrl/Cmd + C` — копировать;
- `Ctrl/Cmd + V` — вставить в открытую папку.

На touch-устройствах обычный тап продолжает сразу открывать объект, чтобы мобильный сценарий не требовал двойного нажатия.

Буфер MaterCMS внутренний и сохраняется в пределах текущей вкладки. После копирования можно перейти в другую папку и вставить копию объекта. Если у пользователя есть необходимые права в другом проекте, копию можно вставить и туда.

При копировании **раздела** MaterCMS создаёт независимую копию текущей схемы, значений, переводов и начального состояния истории версий. При копировании **папки** копируется всё дерево папок и разделов внутри неё. Upload-файлы физически не дублируются: обе копии безопасно ссылаются на существующий файл, а автоочистка удалит файл только когда на него больше не останется ссылок.

Если в папке назначения уже есть объект с таким именем, MaterCMS автоматически подбирает свободное имя (`— копия`, `— копия (2)` и т. п.). Перемещение папки внутрь самой себя или любой дочерней папки блокируется.

Если курсор находится в `input`, `textarea`, `select`, `contenteditable` или на странице выделен текст, MaterCMS **не перехватывает** `Ctrl/Cmd+C/X/V`: работают обычные системные операции браузера.


# 4. Проекты

MaterCMS может обслуживать несколько независимых сайтов или приложений.

У каждого проекта свои:

- контент и папки;
- глобальные «Данные»;
- файлы;
- формы и заявки;
- языки;
- API;
- участники и права.

## 4.1 Выбор проекта

Откройте:

```text
Настройки → Проекты
```

Страница показывает карточки всех доступных проектов. Текущий проект отмечен статусом **«Текущий»**.

Чтобы сменить рабочее пространство, нажмите **«Открыть проект»** на нужной карточке.

Переключателя проекта в header нет — это специально сделано, чтобы случайно не начать редактировать другой сайт.

## 4.2 Создание проекта

Владелец CMS:

1. открывает **Настройки → Проекты**;
2. нажимает **«Новый проект»**;
3. вводит название;
4. MaterCMS создаёт отдельное рабочее пространство и стабильный API namespace.

Переименование видимого названия проекта не меняет уже созданный API slug.

## 4.3 Проект, участники и роли

Ниже карточек отображается панель выбранного проекта. В ней находятся:

- полный API URL;
- переименование;
- удаление проекта, если это разрешено;
- выбор проекта для управления доступом;
- участники проекта;
- роль каждого участника;
- точные разрешения поверх выбранной роли.

Именно **Проекты** являются единственным местом, где назначается доступ пользователя к рабочему пространству. Чтобы добавить человека, сначала создайте его учётную запись в **Настройки → Команда**, затем откройте **Настройки → Проекты**, выберите проект и нажмите **«Добавить участника»**.

Переключение проекта на этой странице не выбрасывает пользователя из настроек: MaterCMS остаётся в разделе «Проекты» и сразу загружает участников выбранного рабочего пространства.

Удаление проекта всегда требует подтверждения и недоступно, если это единственный проект MaterCMS.

# 8. Данные

**Данные** — отдельная глобальная область проекта. Они не находятся внутри папок и не привязаны к одной странице сайта.

Используйте её для информации, которая должна существовать в одном месте и использоваться в разных разделах frontend:

- товары;
- услуги;
- сотрудники;
- отзывы;
- категории;
- тарифы;
- настройки;
- контакты;
- FAQ.

Например `Данные → Товары` можно одновременно использовать на главной странице, в каталоге и в блоке популярных товаров. Сами товары при этом хранятся только один раз.

## 8.1 Создание данных

1. Откройте **Данные** в основной навигации.
2. Нажмите **Создать данные**.
3. Введите название.
4. При необходимости укажите `slug`. Если оставить его пустым, MaterCMS создаст адрес автоматически.
5. Выберите тип **Single** или **Multiple**.
6. После создания добавьте поля.

## 8.2 Single

`Single` хранит один объект. Списка записей нет — после открытия пользователь сразу редактирует значения.

Подходит для контактов, настроек сайта, реквизитов компании или социальных сетей.

Пример ответа:

```json
{
  "phone": "+7 700 000 00 00",
  "email": "hello@example.com"
}
```

## 8.3 Multiple

`Multiple` хранит список однотипных объектов. Записи теперь показываются как обычный **Grid / List**, поэтому большой набор данных не превращается в длинную форму редактора.

В верхней части набора рядом с кнопкой **«Поля»** находится кнопка **«Создать»**. Она создаёт новую запись и открывает её редактор.

Нажатие на существующую карточку или строку записи открывает простое меню действий:

- **Читаемый вид** — показывает все поля без элементов ввода;
- **Редактировать** — открывает запись в модальном редакторе;
- **Удалить** — запрашивает подтверждение и удаляет запись.

Переключатель **Grid / List** запоминается в браузере. Та же модель используется для обычных разделов типа **«Много»**, чтобы работа с повторяющимся контентом и глобальными данными ощущалась одинаково.

Подходит для товаров, услуг, сотрудников, отзывов, категорий и FAQ.

Пример:

```json
[
  { "id": 1, "name": "Товар 1", "price": 12000 },
  { "id": 2, "name": "Товар 2", "price": 18000 }
]
```

MaterCMS автоматически назначает каждой записи `Multiple` стабильный `id`. Пользователю не нужно управлять им вручную — он нужен для API и связей между данными.

## 8.4 Поля данных

В данных доступны текст, textarea, число, boolean, дата, дата и время, select, изображение, видео, аудио, файл и **Связь**. Для файловых полей можно включить множественную загрузку.

Изменения значений и структуры сохраняются автоматически. Кнопка сохранения не нужна.

## 8.5 Поле «Связь»

**Связь** позволяет выбрать одну или несколько записей из другого набора данных. Она нужна, когда одинаковая информация должна храниться в одном месте, но использоваться в других данных.

Например:

```text
Данные
├── Категории
│   ├── Ноутбуки
│   ├── Смартфоны
│   └── Аксессуары
│
└── Товары
    ├── MacBook Air → Ноутбуки
    ├── iPhone → Смартфоны
    └── AirPods → Аксессуары
```

Категории при этом не являются специальной функцией MaterCMS. Это обычный набор **Multiple**, который можно связать с товарами, статьями, услугами или любыми другими данными.

### Создание связи

1. Откройте нужный набор данных, например **Товары**.
2. Откройте **Поля**.
3. Добавьте новое поле и задайте понятное название.
4. Выберите тип **Связь**.
5. Проверьте `slug` поля — это ключ, который будет использоваться в API.
6. В поле **Источник** выберите другой набор данных.
7. Выберите режим:
   - **Одна запись**;
   - **Несколько записей**.
8. При необходимости выберите **Показывать по полю**.

В качестве источника MaterCMS показывает только данные типа **Multiple**. `Single` в этом списке не отображается.

Пример:

```text
Название: Категория
Slug: category
Тип: Связь
Источник: Категории
Выбор: Одна запись
```

### Как MaterCMS показывает записи

По умолчанию MaterCMS выбирает понятное название автоматически в таком порядке:

1. поле `name`;
2. поле `title`;
3. первое текстовое поле;
4. если текста нет — `Запись #ID`.

Если автоматический вариант не подходит, в настройке поля можно выбрать **Показывать по полю**.

### Выбор записи

При нажатии на поле связи открывается отдельное окно со строкой поиска. Поэтому даже при большом количестве категорий, сотрудников или товаров не нужно работать с длинным системным select.

Для одной связи выбирается одна запись. Для множественной можно отметить несколько записей и снять выбор позже.

MaterCMS сохраняет саму связь, а не копию названия. Поэтому если:

```text
Ноутбуки
↓
Ноутбуки и компьютеры
```

товар останется связан с той же записью, и новое название появится автоматически.

### Примеры использования

Одно и то же поле «Связь» подходит для разных сценариев:

```text
Товар → Категория
Товар → Бренд
Товар → несколько категорий
Статья → Автор
Статья → несколько категорий
Сотрудник → Отдел
Услуга → Направления
```

Для категорий, брендов, авторов и отделов не нужно создавать отдельные специальные модули.

### Удаление связанных записей

Если удалить запись, которая была выбрана в других данных, сами связанные объекты не удаляются.

Например:

```text
Удалили «Ноутбуки»
↓
MacBook Air остаётся
↓
поле «Категория» становится пустым
```

Если связь множественная, MaterCMS удалит из списка только удалённую запись, а остальные связи сохранятся.

### Удаление целого набора

MaterCMS не позволит удалить набор данных, пока другие данные используют его как источник связи.

Например будет показано:

```text
Невозможно удалить «Категории»

Этот набор используется в других данных:
• Товары → Категория
• Статьи → Категория
```

Сначала удалите соответствующие поля **Связь**, после чего набор можно удалить.


### 8.0 Маршрутизация public API на Apache и nginx

MaterCMS не предполагает, что `.htaccess` поддерживается везде. В `config.php` есть параметр:

```php
'api_route_mode' => 'auto',
```

В режиме `auto`:

- Apache/LiteSpeed → clean URL вида `/cms/api/main/home/seo`;
- nginx, Caddy, PHP built-in server и неизвестные серверы → direct URL вида `/cms/api/index.php?path=main/home/seo`.

Оба варианта ведут в один и тот же `cms/api/index.php` и возвращают одинаковый JSON. API offcanvas, формы, данные и AI Prompt получают URL через единый серверный генератор, поэтому копируемый endpoint соответствует текущему окружению.

При необходимости можно явно задать:

```php
'api_route_mode' => 'pretty', // если rewrite настроен вручную
// или
'api_route_mode' => 'direct', // всегда использовать index.php?path=...
```

На nginx старый clean URL `/cms/api/main/...` не может быть перехвачен PHP без nginx rewrite. Поэтому MaterCMS в `auto` не генерирует такой URL на nginx и использует direct route, который работает без изменения конфигурации сервера.

Параметры `lang`, `meta=1` и `meta=0` добавляются к direct URL обычным способом, например:

```text
https://example.com/cms/api/index.php?path=main/home/seo&lang=kk&meta=1
```

## 8.6 API данных

В открытом наборе нажмите **API**. Справа откроется панель подключения. Она показывает состояние API набора, режим доступа проекта, полный endpoint, тип ответа (`Object` или `Array`) и готовые примеры для JavaScript, PHP, Python и cURL. Адрес и пример кода можно скопировать одной кнопкой.

В этой же панели есть блок **AI Prompt**:

- **Копировать prompt** — копирует готовое задание для ИИ с endpoint, типом ответа, правилами авторизации и **JSON-примером текущих данных**;
- **Открыть в ChatGPT** — открывает `https://chatgpt.com/?prompt=...` с тем же prompt и JSON-примером в строке ввода.

MaterCMS никогда не добавляет реальный private API token в AI prompt. Для приватного API prompt только указывает использовать `MATERCMS_API_TOKEN` на backend/serverless.

У каждого набора свой read-only endpoint. Ниже показан clean-вариант для Apache/LiteSpeed; на nginx MaterCMS автоматически покажет эквивалентный `api/index.php?path=...` URL:

```text
GET https://example.com/cms/api/{project-slug}/data/{data-slug}
```

Например:

```text
GET https://example.com/cms/api/main/data/contacts
GET https://example.com/cms/api/main/data/products
```

`Single` возвращает объект, `Multiple` — массив. Записи `Multiple` также получают стабильный `id`, который MaterCMS использует для связей.

Обычный ответ:

```json
[
  {
    "id": 1,
    "name": "MacBook Air",
    "price": 529990
  }
]
```

Если в данных есть поле **Связь**, MaterCMS раскрывает выбранную запись автоматически. Frontend не нужно отдельно превращать непонятный ID в категорию:

```json
[
  {
    "id": 1,
    "name": "MacBook Air",
    "price": 529990,
    "category": {
      "id": 2,
      "name": "Ноутбуки",
      "slug": "laptops"
    }
  }
]
```

Для множественной связи возвращается массив объектов:

```json
[
  {
    "id": 1,
    "name": "MacBook Air",
    "categories": [
      {
        "id": 2,
        "name": "Ноутбуки"
      },
      {
        "id": 5,
        "name": "Новинки"
      }
    ]
  }
]
```

Связи раскрываются только **на один уровень**. Это защищает API от бесконечных цепочек, например когда два набора ссылаются друг на друга.

Для каждого набора отдельно можно выключить внешний API. Если API набора выключен, endpoint недоступен, но данные продолжают храниться и редактироваться внутри MaterCMS.

Публичный API данных поддерживает только `GET`. Создание, изменение и удаление данных через внешний API запрещены.

Если весь проект переведён в **Приватный API**, endpoint данных также требует проектный Bearer-токен. Сам токен нельзя помещать во frontend-код.

## 8.7 Формат ответа API проекта

Формат ответа настраивается в **Настройки → Доступ к API → Полный ответ API**. Это серверная настройка текущего проекта, поэтому она не зависит от браузера и сохраняется после выхода из админки.

По умолчанию используется режим **Только данные**:

```json
{
  "title": "Главная"
}
```

Для `Multiple` это обычный JSON-массив. Успешный POST формы в компактном режиме возвращает:

```json
{
  "ok": true,
  "message": "Спасибо! Данные отправлены."
}
```

Если включить **Полный ответ**, GET разделов и наборов данных возвращает envelope:

```json
{
  "data": {
    "title": "Главная"
  },
  "meta": {
    "project": {
      "name": "Мой проект",
      "slug": "main"
    },
    "name": "SEO",
    "mode": "single",
    "returns": "object",
    "updated_at": "...",
    "path": "/cms/api/main/home/seo",
    "url": "https://example.com/cms/api/main/home/seo"
  }
}
```

Для мультиязычного раздела `meta` дополнительно содержит параметры языка. Для формы полный успешный ответ содержит служебные идентификаторы:

```json
{
  "ok": true,
  "message": "Спасибо! Данные отправлены.",
  "submission_id": 123,
  "project": "main",
  "form": "contact"
}
```

Корневой endpoint проекта (clean `GET /api/{project-slug}/` либо direct `GET /api/index.php?path={project-slug}`) всегда остаётся картой API и сообщает текущий `response_mode`. Один конкретный запрос можно переопределить без изменения настройки проекта:

```text
?meta=1   → принудительно полный ответ
?meta=0   → принудительно только данные
```

MaterCMS также отправляет заголовок `X-MaterCMS-Response-Mode: full|data`, отражающий фактический режим текущего запроса.

### API offcanvas

В каждой API-панели — папки, раздела, данных и формы — отображается тот же серверный переключатель формата. Изменение в любой панели сразу меняет настройку всего текущего проекта. Рядом отображается отдельный switch доступности текущего endpoint; для корневой API-панели используется мастер-переключатель проекта.

Ниже endpoint находится spoiler **«Какой ответ вернёт API»**. Он всегда закрыт при открытии offcanvas и показывает JSON-пример именно для текущего режима. Это позволяет проверить форму ответа до подключения frontend/backend. Верхние статусные карточки offcanvas объединены общим `gap`, поэтому расстояния между ними одинаковы во всех темах и на разных ширинах.

AI Prompt тоже учитывает настройку: при полном режиме пример содержит `data + meta`, а при компактном — чистый объект/массив. Для формы prompt показывает отдельно JSON запроса и JSON успешного ответа.


## 8.8 API папок и управление доступностью endpoint

### Рекурсивный Folder Tree API

Любая пользовательская папка в **Мой контент** имеет собственный read-only GET endpoint. Folder API всегда раскрывает всю включённую ветку рекурсивно — без отдельной настройки глубины.

Clean URL на Apache/LiteSpeed:

```text
GET https://example.com/cms/api/{project-slug}/{folder-slug}
```

На nginx/другом сервере MaterCMS автоматически показывает direct URL:

```text
GET https://example.com/cms/api/index.php?path={project-slug}/{folder-slug}
```

В каждом узле:

- `folders` — все включённые вложенные папки;
- `sections` — все включённые разделы непосредственно внутри папки;
- папки и разделы с собственным `api_enabled=false` не попадают в дерево;
- каждая вложенная папка повторяет ту же структуру.

### Формат ответа управляет содержимым дерева

Folder API больше не имеет отдельного переключателя **«Данные разделов»**. Источником истины является проектная настройка **Формат ответа**.

#### Только данные

В этом режиме MaterCMS возвращает **всю структуру** папки, но не загружает содержимое разделов. Раздел остаётся в `sections` как информационный объект:

```json
{
  "type": "folder",
  "name": "Каталог",
  "slug": "catalog",
  "folders": [
    {
      "type": "folder",
      "name": "Ноутбуки",
      "slug": "laptops",
      "folders": [],
      "sections": [
        {
          "type": "section",
          "name": "SEO",
          "slug": "seo",
          "mode": "single",
          "path": "/cms/api/main/catalog/laptops/seo",
          "url": "https://example.com/cms/api/main/catalog/laptops/seo"
        }
      ]
    }
  ],
  "sections": []
}
```

Такой режим подходит для навигации, маршрутизации, генерации меню и предварительного построения frontend без загрузки тяжёлого контента.

#### Полный ответ

В полном режиме MaterCMS проходит ту же рекурсивную структуру, но каждый раздел дополнительно получает `data`. Результат оборачивается в `{ data, meta }`:

```json
{
  "data": {
    "type": "folder",
    "name": "Каталог",
    "folders": [],
    "sections": [
      {
        "type": "section",
        "name": "SEO",
        "slug": "seo",
        "mode": "single",
        "data": {
          "title": "Каталог"
        }
      }
    ]
  },
  "meta": {
    "type": "folder-tree",
    "recursive": true,
    "response_mode": "full",
    "cache": {
      "enabled": true,
      "ttl": 60,
      "status": "hit"
    }
  }
}
```

`?meta=1` и `?meta=0` по-прежнему позволяют переопределить формат конкретного запроса. Для Folder API это также автоматически переключает наличие содержимого `data`.

### Кеш готового JSON

Это единственная отдельная настройка Folder API. Для каждой папки можно выбрать TTL:

- `0` — выключен;
- `30` — 30 секунд;
- `60` — 1 минута;
- `300` — 5 минут;
- `900` — 15 минут;
- `3600` — 1 час.

MaterCMS кеширует уже собранное дерево. Компактная структура и полный ответ имеют разные cache keys, поэтому тяжёлый полный JSON никогда не подменяет лёгкую структурную версию и наоборот.

Backend выбирается автоматически:

1. APCu — быстрый RAM-cache, если расширение доступно;
2. файловый fallback в системном временном каталоге — если APCu недоступен.

После изменений контента, структуры, переводов или API switches ревизия деревьев обновляется, поэтому старый JSON не продолжает отдаваться до окончания TTL.

Диагностические заголовки:

```text
X-MaterCMS-Tree-Cache: HIT | MISS | BYPASS
X-MaterCMS-Tree-Content: FULL | STRUCTURE
```

### Включение и выключение API

API проекта остаётся главным выключателем. Дополнительно собственный switch есть у папки, раздела, набора **Данные** и формы.

- папка off → её direct Folder API отвечает `404` и она не включается в родительское дерево;
- раздел off → direct endpoint отвечает `404` и раздел не включается в `sections`;
- Данные off → endpoint набора отвечает `404`;
- форма off → GET descriptor и POST приёма заявок отвечают `404`;
- проект off → блокируется весь namespace проекта.

Отдельного режима «скрыть только из дерева родителя» больше нет: структура Folder API следует фактическим включённым API-объектам.

## 8.9 Упрощённая модель Folder Tree API

Начиная с версии **2026.09.10.16**, настройки глубины рекурсии, `api_tree_include_data` и ручного выбора веток исключены из пользовательской модели. Старая схема БД может сохранять совместимые служебные колонки после обновления существующей установки, но runtime их больше не использует при построении Folder API.

Источник истины теперь простой:

```text
Структура папок MaterCMS
        +
API enabled каждого объекта
        +
Формат ответа проекта
        +
TTL кеша папки
        ↓
Folder Tree API
```

Это убирает дублирующие настройки и делает поведение endpoint предсказуемым.


# 9. Автосохранение

В MaterCMS нет основной кнопки «Сохранить» для редактирования контента, данных и структуры форм.

Работа происходит так:

```text
Изменение поля
↓
короткая пауза
↓
Сохраняем…
↓
Сохранено
```



## 9.1 Можно продолжать редактирование во время сохранения

Автосохранение работает в фоне. Пользователю не нужно ждать окончания запроса перед тем, как продолжить ввод.

Если во время состояния **Сохраняем…** были внесены новые изменения, MaterCMS не заменяет редактор старым ответом сервера. Новые изменения остаются в интерфейсе и автоматически отправляются следующим сохранением.

Это относится к:

- значениям обычных разделов;
- названиям и типам полей;
- данным `Single / Multiple`;
- полям **Связь**;
- формам;
- загрузке и замене файлов.

## 9.2 Состояния сохранения

В интерфейсе могут отображаться состояния:

- **Сохраним через секунду** — есть локальные изменения, ожидается короткая пауза;
- **Сохраняем…** — данные отправляются на сервер;
- **Сохранено** — сервер подтвердил текущую версию;
- **Не удалось сохранить** — возникла ошибка сети или сервера.

При ошибке MaterCMS не должен сбрасывать введённые значения. Исправьте соединение или продолжите редактирование — следующее изменение снова запустит автосохранение.

## 9.3 Переходы между разделами

При переходе в другую папку, форму, набор данных или проект MaterCMS сначала завершает ожидающее автосохранение.

Если сохранить изменения не удалось, переход блокируется и CMS предупреждает пользователя, чтобы последние правки не потерялись. То же правило применяется к кнопкам Back/Forward браузера.

При закрытии вкладки браузер также предупреждает, если сохранение ещё не завершено.

> Во время обычной работы не требуется вручную обновлять страницу после сохранения. Редактор остаётся на месте, а курсор и активное поле не должны сбрасываться.

# 10. Версии

MaterCMS автоматически создаёт историю изменений.

Чтобы история не заполнялась новой версией после каждой введённой буквы, близкие автосохранения объединяются в одну рабочую версию.

Чтобы восстановить старое состояние:

1. Откройте нужный раздел.
2. Нажмите **Версии**.
3. Выберите нужную дату/версию.
4. Нажмите восстановление.
5. Подтвердите действие в модальном окне MaterCMS.

Старые файлы сохраняются на диске, пока они нужны одной из доступных версий. Когда версия удаляется из истории и файл больше нигде не используется, MaterCMS может удалить его автоматически.

- название файла;
- тип;
- размер;
- кнопка закрытия;

- PDF — встроенный просмотр документа;

Во время предпросмотра MaterCMS блокирует прокрутку страницы: системный scrollbar основного интерфейса скрывается, а файл всегда остаётся внутри доступной высоты окна. Для PDF прокрутка выполняется внутри самого документа.

Также работают клавиши:

```text
← / →    соседний файл
Esc      закрыть предпросмотр
```

## 11.5 Неиспользуемые файлы

MaterCMS отслеживает, где используется каждый файл.

Файл может быть:

- используется текущим контентом;
- используется формой/заявкой;
- нужен только старой версии;
- не используется.

Команда очистки удаляет только те файлы, на которые больше нет рабочих ссылок и которые не нужны истории версий.

# 14. Пользователи и права

Управление разделено на два понятных уровня.

### Учётные записи

Глобальный справочник пользователей находится в:

```text
Настройки → Команда
```

Этот раздел доступен владельцу MaterCMS и отвечает **только за учётные записи**. Здесь можно:

- создать пользователя;
- изменить имя и email;
- при необходимости задать новый пароль;
- удалить обычную учётную запись.

Проекты, роли и права в форме пользователя не выбираются. Это специально сделано, чтобы доступ не управлялся из двух разных мест.

## 14.1 Создание пользователя

Нажмите **«Новый пользователь»** и укажите:

- имя;
- email;
- пароль минимум из 8 символов.

После создания пользователь ещё не обязан иметь доступ к какому-либо проекту. Назначение выполняется отдельно в разделе **Настройки → Проекты**.

## 14.2 Редактирование и удаление

При редактировании можно изменить имя, email и, при необходимости, пароль. Сохранение формы пользователя **не меняет** его проектные назначения, роли или точные разрешения.

На карточке обычного пользователя есть кнопка **«Удалить»**. После подтверждения удаляется учётная запись и её назначения в проектах, но контент проектов не удаляется.

MaterCMS не позволяет удалить:

- собственную текущую учётную запись;
- владельца CMS.

## 14.3 Назначение пользователя в проект

Откройте:

```text
Настройки → Проекты
```

В блоке **«Участники проекта»** выберите нужный проект. Затем нажмите **«Добавить участника»**, выберите существующую учётную запись и назначьте роль.

Внутри каждого проекта доступны роли:

- **Владелец**;
- **Администратор**;
- **Редактор**;
- **Только просмотр**.

Один человек может иметь разные роли в разных проектах.

## 14.4 Точные права

В редакторе участника можно дополнительно изменить разрешения независимо от базовой роли:

- просмотр/редактирование контента;
- просмотр/редактирование данных;
- формы;
- файлы;
- настройки;
- участников;
- параметры проекта.

Права проверяются и во Vue-интерфейсе, и на PHP backend API.


## Модальные окна на мобильных устройствах

В MaterCMS полноэкранный режим применяется **только на мобильных экранах**. Для записей типа `Multiple` экран действий, читаемый вид, редактирование и выбор связанных записей открываются на всю ширину и высоту телефона без внешних отступов. На планшетах и desktop сохраняются обычные центрированные модальные окна ограниченной ширины.


## Адаптив авторизации и первого запуска

Авторизация и установщик используют полноэкранную оболочку `100dvh`. Экран входа имеет отдельную завершённую responsive-систему для разных классов устройств.

На широком desktop сохраняется двухколоночная композиция: слева находится продуктовая MaterCMS-панель, справа — форма входа. Начиная с **2026.09.11.18**, пропорции desktop-композиции дополнительно выровнены для реальных ноутбуков и Windows с масштабированием 125%: продуктовая часть держит около `42%` ширины вместо прежнего резкого сжатия, а форма ограничена более спокойной шириной `440–460px` и центрируется внутри правой зоны. Мобильный wordmark имеет отдельный высокоспецифичный desktop-reset и не может дублировать основной логотип слева. При небольшой высоте правый блок получает естественный scroll вместо обрезания формы.

При ширине `960px` и меньше продуктовая панель скрывается, а авторизация превращается в одну колонку на всю ширину viewport. Контент ограничен читаемой шириной и центрируется; сверху отображается компактный MaterCMS wordmark с `safe-area` отступами. На обычной высоте эта бренд-панель sticky, а на коротких landscape-экранах становится частью обычного потока, чтобы не отнимать место у полей.

Для телефонов используются увеличенные touch-friendly поля и кнопка. Текст `input` остаётся не меньше `16px`, поэтому iOS Safari не выполняет автоматический zoom при фокусе. Для экранов до `360px` отдельно уменьшены горизонтальные отступы и скорректирована сетка password-поля, чтобы иконка показа пароля, placeholder и security note не создавали горизонтальный overflow. Светлая и тёмная темы используют одну и ту же responsive-геометрию.

| Контекстное меню с клавиатуры | `Shift+F10` или клавиша Menu |
| Универсальный поиск | `Ctrl/Cmd+F`, `Ctrl/Cmd+E`, `Ctrl/Cmd+K` или `F3` |

Стрелки перемещают текущее выделение; с `Shift` расширяют диапазон. `Home` и `End` переходят к первому и последнему объекту. В context menu доступны те же операции, а также **Копировать путь**, **Свойства**, **Инвертировать выделение** и вставка непосредственно в выбранную папку.

### Визуальный принцип

Функции ОС не диктуют внешний вид. На странице используются обычные MaterCMS breadcrumbs, карточки папок/разделов, компактные кнопки вида/сортировки и контекстная панель, которая появляется только при выделении. Постоянной Windows-like command bar и адресной строки нет.

### Drag & drop

Выделенные объекты можно перетянуть в папку. Любой drop создаёт копию в целевой папке и не меняет расположение исходного объекта. Для множественного выделения дочерний объект не дублируется отдельно, если вместе с ним уже выбрана родительская папка.

### Корзина

`Delete` больше не уничтожает папку или раздел сразу. Объект переносится во внутреннюю корзину проекта и исчезает из **Мой контент**, дерева папок, глобального поиска и публичного content API. В корзине можно выбрать несколько объектов, восстановить их, удалить навсегда или очистить корзину целиком. Если исходная папка больше не существует, восстановление идёт в корень проекта. Конфликты имён разрешаются автоматически.

`Shift+Delete` остаётся прямым необратимым удалением и всегда требует подтверждения.

### Undo / Redo

В рамках текущей вкладки MaterCMS хранит историю проводника для переименования, копирования и отправки в корзину. Поддерживаются `Ctrl/Cmd+Z` и `Ctrl/Cmd+Y` / `Ctrl/Cmd+Shift+Z`. История сбрасывается естественно при перезагрузке вкладки и не подменяет серверную историю версий содержимого разделов.

### Вид и сортировка

Доступны Grid/List и сортировка по имени, типу и дате изменения. Сортировка открывается отдельным dropdown по нажатию на кнопку и внутри позволяет выбрать поле и направление по возрастанию/убыванию. Breadcrumb, статус количества элементов и состояние внутреннего буфера остаются частью страницы. Выбранный объект можно открыть в новой вкладке или посмотреть его свойства.

MaterCMS намеренно повторяет только файловые операции, которые логичны для headless CMS. Функции ОС, связанные с дисками, NTFS, приложениями, архивированием и исполняемыми файлами, не имитируются.

## 2026-09-10 — Связанные «Данные» и «Формы» внутри «Мой контент»

В меню **Создать** раздела **Мой контент** добавлены пункты **Данные** и **Форма**. Они не создают дубликаты. После выбора пункта MaterCMS открывает модальное окно со всеми уже созданными ресурсами соответствующего типа; checkbox определяет, какие из них должны отображаться в текущей папке. Повторное открытие модального окна показывает фактические текущие связи, а снятие checkbox удаляет только связь с папкой.

Связь хранится в таблице `content_links` как `project_id + folder_id + resource_type + resource_id`. Имя, slug, режим, API-состояние, содержимое и другие свойства не копируются в связь и всегда читаются из `data_sets` или `forms`. Поэтому связанный объект автоматически следует за исходной сущностью — источник истины остаётся один. Один набор данных или форма может быть связан с несколькими папками. При удалении исходного ресурса его связи очищаются; при глубоком копировании папки связи копируются как ссылки на те же исходные ресурсы.

В интерфейсе связанные ресурсы отображаются отдельными MaterCMS-карточками с меткой **«Связано»**. Открытие карточки ведёт в исходный набор данных или форму. Счётчик содержимого папки учитывает связанные ресурсы.

Folder API отражает композицию папки: кроме `folders` и `sections` в JSON добавлены массивы `data_sets` и `forms`. В режиме **Только данные** связанные ресурсы присутствуют как информационная структура (`name`, `slug`, `mode/method`, `url`) без тяжёлого содержимого. В режиме **Полный ответ** `data_sets` дополнительно содержат актуальный `data`, а `forms` — актуальную `schema` и `success_message`. Ресурс с выключенным собственным API в публичное дерево не включается. Изменение связей или исходных ресурсов инвалидирует кеш дерева через общую ревизию API.

## 2026-09-10 — Исправление сохранения связанных ресурсов

Исправлена ошибка `SQLSTATE[HY000]: ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`, возникавшая при добавлении существующих Data/Form в папку через checkbox. Причина была в реализации `Database::insertIgnore()`: для SQLite/PostgreSQL conflict target ошибочно строился из всех полей вставки, включая `sort_order`, хотя уникальность `content_links` определяется комбинацией `project_id + folder_id + resource_type + resource_id`. Теперь используются нативные варианты `INSERT OR IGNORE` (SQLite), `ON CONFLICT DO NOTHING` без conflict target (PostgreSQL) и `INSERT IGNORE` (MySQL).

## 2026-09-10 — Связанные Данные и Формы как элементы «Мой контент»

Связанные ресурсы больше не являются пассивными карточками. `resource-link` включён в общую модель выбора и clipboard «Мой контент»: один клик выделяет, двойной открывает исходный ресурс, работают `Ctrl/Cmd+C`, `Ctrl/Cmd+V`, copy-only drag & drop между папками, множественное выделение, `Ctrl+A`, свойства и context menu.

Копирование создаёт новую связь на тот же исходный Data Set / Form в папке назначения. Перемещение изменяет только расположение связи. Сам набор данных или форма не копируются и не меняют источник истины. Дублирование одной и той же связи в одной папке блокируется.

Удаление `resource-link` означает **«Убрать из папки»** и не удаляет исходный ресурс. Для такой операции поддержаны Undo/Redo через восстановление ссылки. Папки и обычные разделы продолжают использовать Корзину.

## 2026-09-10 — Production hardening и автодиагностика

На первом запуске MaterCMS самостоятельно проверяет минимальное production-окружение. При каждом релизе обе копии полностью перезаписываются одной и той же строкой. История изменений остаётся в `VERSION.md`.

## 2026-09-11 — `commit.md` для `git commit -m`

Начиная с версии **2026.09.11.6**, текущий Git commit message хранится одновременно в корне проекта и внутри `cms`. Это удобно и когда Git-команды запускаются из корня, и когда рабочий процесс ориентирован на каталог CMS.

Оба файла содержат только одну строку:

```text
chore(git): keep commit message in root and cms
```

Для Windows CMD из корня проекта:

```bat
set /p COMMIT_MSG=<commit.md
git commit -m "%COMMIT_MSG%"
```

Файлы `/commit.md` и `/cms/commit.md` должны оставаться синхронными при каждом следующем изменении MaterCMS.
## 2026-09-11 — Password visibility control

Все поля `type="password"` в MaterCMS используют общий UI-контрол показа/скрытия пароля. Он подключён в установщике для пароля СУБД и первого администратора, на странице входа, в окне смены подключения к БД и в создании/редактировании пользователя.

Обработчик находится в `cms/assets/ui.js` и использует делегирование событий по `data-password-toggle`, поэтому один скрипт обслуживает статические PHP-формы и динамические Vue-модальные окна. При показе поле временно переключается в `type="text"`, при скрытии возвращается в `type="password"`; значение поля не копируется и не сохраняется отдельно. Кнопка имеет доступные `aria-label`, `aria-pressed` и focus-visible состояния.
## 2026.09.11.8 — Production UX: copy-only content, navigation delay, preloader, Trash checkbox

### «Мой контент»: только копирование

Функция **«Вырезать»** удалена полностью. В интерфейсе больше нет команды «Вырезать», сочетания `Ctrl/Cmd+X`, cut-state карточек и cut-clipboard. Backend `paste_content` теперь выполняет только копирование. Drag & drop также создаёт копию в целевой папке и не перемещает исходный объект.

### SPA-переходы

Перед применением внутреннего SPA-маршрута MaterCMS выдерживает **250 мс**. Это единая пауза для переходов между папками, разделами, Данными, Формами и Настройками через функцию `navigate()`.

### Глобальный server-preloader

`cms/assets/ui.js` оборачивает глобальный `window.fetch`. Для каждого запроса отдельно запускается порог **100 мс**. Если запрос успел завершиться раньше — overlay не создаёт визуального всплеска. Если запрос длится дольше, MaterCMS показывает слой `100vw × 100dvh` с `backdrop-filter: blur(...) brightness(...)` и центральным spinner. При параллельных медленных запросах overlay остаётся до завершения последнего из них.

### Корзина

Каждая строка Корзины получила настоящий checkbox. Пользователь может независимо отметить несколько объектов, использовать **«Выбрать всё»**, затем восстановить или удалить навсегда только выбранные позиции. `Ctrl/Cmd+A` внутри Корзины продолжает выбирать все элементы, `Delete` удаляет выбранные навсегда после подтверждения.
## 2026.09.11.9 — Smart Loading Manager

### Route navigation

Фиксированная задержка `250 ms` удалена. `navigate()` теперь сразу начинает переход и загрузку данных. Перед началом запроса MaterCMS определяет тип целевого route и включает соответствующий skeleton:

- `explorer` — Мой контент, Файлы, Данные, Формы;
- `editor` — Раздел, Data Set, Form;
- `settings` — общие настройки, API, языки, база данных;
- `management` — Проекты и Команда.

Skeleton имеет минимальное окно стабильности **120 ms**, но это не задержка перед запросом: backend-запрос начинается немедленно. Если сервер отвечает дольше, skeleton просто остаётся до фактической готовности route. После загрузки MaterCMS ждёт два animation frame, чтобы Vue успел отрисовать готовый экран без промежуточного мерцания.

### Long-request preloader

Глобальный `fetch`-preloader из предыдущей версии сохранён для долгих операций вне навигации. Во время активного route-skeleton корневому `<html>` добавляется класс `matercms-route-loading`, и полноэкранный blur-overlay подавляется. Поэтому навигация показывает только контекстный skeleton, а сохранения/удаления/другие долгие server operations по-прежнему получают глобальную обратную связь.

### In-page skeletons

Состояния загрузки для списков проектов, пользователей, файлов, данных, форм, настроек, Корзины, истории версий, relation picker и выбора связанных ресурсов визуально переведены на skeleton surfaces. Это создаёт единый loading-language по всему MaterCMS вместо смеси spinner-ов и пустых блоков.

### Reduced motion

При `prefers-reduced-motion: reduce` входная анимация skeleton отключается, а shimmer замедляется.

## О продукте / Product Hub

MaterCMS имеет отдельный внутренний путь `?about=1`, доступный авторизованным пользователям из боковой навигации и из главной страницы настроек. Product Hub не хранит копию changelog во Vue-коде: backend читает Markdown-файлы текущей сборки и отдаёт структурированные данные интерфейсу.

Страница показывает бренд и текущую версию, автора MaterCMS, стек, runtime PHP, активную СУБД, режим API routing, число релизов и актуальную строку из `commit.md`. История релизов разбирается из заголовков `## YYYY.MM.DD.N — ...` файла `VERSION.md`; разделы `###` и маркированные изменения отображаются в раскрывающемся timeline со встроенным поиском.

Карточки `README.md`, `DOCUMENTATION.md`, `VERSION.md` и `commit.md` загружаются по требованию через admin API и открываются во встроенном безопасном Markdown Viewer. Сырой Markdown не внедряется напрямую в DOM: frontend экранирует HTML и форматирует только поддерживаемую Markdown-разметку.

Backend endpoints Product Hub:

- `GET cms/api/admin.php?action=product_about` — метаданные продукта, список документов и структурированная история релизов;
- `GET cms/api/admin.php?action=product_document&document=readme|documentation|versions|commit` — содержимое разрешённого Markdown-файла.

Пути файлов заданы whitelist-списком на сервере; произвольный путь через query-параметр открыть нельзя.
## Product Hub и расположение Markdown

Раздел **«О продукте»** не зависит от того, опубликован ли весь корень MaterCMS. Backend сначала ищет синхронные runtime-копии `README.md`, `DOCUMENTATION.md`, `VERSION.md` и `commit.md` непосредственно в каталоге `cms/`, после чего использует файлы из корня проекта как fallback. Это важно для shared hosting и конфигураций, где web-root указывает непосредственно на CMS-каталог. Пустой или отсутствующий файл помечается как недоступный и не открывается в Markdown Viewer.

## Product Hub: modal Markdown viewer

Начиная с версии **2026.09.11.12**, карточки документов в **О продукте** открывают документацию в отдельном модальном viewer вместо inline-блока внутри страницы.

Поведение viewer:

- открывается для `README.md`, `DOCUMENTATION.md`, `VERSION.md` и `commit.md`;
- использует тот же безопасный whitelist backend endpoint `product_document`;
- показывает skeleton до завершения загрузки Markdown;
- закрывается по `Esc`, кнопке `×` или клику на backdrop;
- защита request sequence не позволяет завершившемуся старому запросу заново открыть уже закрытое окно;
- при открытом viewer блокируется прокрутка основного документа;
- на desktop окно ограничено по ширине и высоте, а Markdown прокручивается внутри;
- на мобильных устройствах viewer становится полноэкранным;
- светлая и тёмная темы используют общие переменные MaterCMS.
## Product Hub: автор и репозитории

Раздел **«О продукте»** является встроенным Product Hub MaterCMS. Он показывает текущую версию из `VERSION.md`, runtime-информацию, текущий `commit.md`, документацию, релизную историю, расширенную карточку автора и список репозиториев.

Текущий публичный репозиторий продукта: `https://github.com/DreamerView/mater-cms`. Структура backend-ответа использует массив `repositories`, поэтому интерфейс готов к нескольким репозиториям без отдельной переработки страницы.

## 2026-09-11 — Фото автора в Product Hub

В разделе **О продукте** профиль автора теперь использует оптимизированную фотографию. MaterCMS хранит две WebP-версии (`256×256` и `512×512`) и выбирает подходящее разрешение через `srcset`, чтобы сохранить чёткость на Retina-дисплеях без лишнего веса. Исходное изображение не стилизуется и не меняется — выполняется только техническая оптимизация для web.
## 2026-09-11 — MaterCMS Icon System

Визуальный язык иконок приведён к единой Apple-inspired системе. Новая система не добавляет внешнюю runtime-зависимость и не использует SF Symbols: базой остаётся Bootstrap Icons, но предпочтение отдаётся outline-вариантам. Icon-only controls используют единый размер, компактный squircle-radius и спокойные hover/active состояния. Иконки настроек, API, файлов, проектов, Product Hub и связанных ресурсов используют общие нейтральные поверхности и semantic tint-акценты. В тёмной теме контраст иконок и подложек задан отдельно, чтобы не появлялись слишком яркие блоки. `prefers-reduced-motion` продолжает учитываться.

## Mobile Safari и модальные поверхности

Начиная с `2026.09.11.16`, MaterCMS не отключает масштабирование страницы через `maximum-scale` или `user-scalable=no`. Вместо этого все текстовые `input`, `select` и `textarea` на экранах до 720 px имеют стабильный computed `font-size: 16px`, что предотвращает автоматический zoom Safari без ухудшения доступности. Размер текста не меняется при `focus`.

Серверные POST-формы установщика и авторизации используют паттерн **Post/Redirect/Get**: после обработки MaterCMS отвечает `303` и открывает чистый GET URL. Ошибки передаются через flash-состояние сессии, а секретные значения БД и пароли в flash не сохраняются. Это устраняет браузерное предупреждение «отправить форму повторно?» после обновления страницы.

Мобильные full-screen поверхности используют единый контракт: fixed backdrop `inset: 0`, `height: 100dvh`, отсутствие внешнего padding, flex-column modal, safe-area для верхней/нижней части и scroll только во внутренней области содержимого. В этот слой входят перенос БД, управление пользователем, просмотр/редактирование записей, relation picker, Product Documentation и полноэкранный просмотр файлов. При открытой модалке scroll документа блокируется.
